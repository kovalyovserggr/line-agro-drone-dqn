## 1. Загальна постановка

Лінія з 26 вузлів (+ додаткові постачальники філаменту id 101+, якщо
`n_filament_suppliers > 1`; у Статті 1 повна сітка — `n=5`). Агент вирішує для
кожного вузла, **коли проводити планове ТО**. Решта логіки (FSM вузла, облік
ресурсів, квоти, вибір операції за правилом D17) — код симулятора без змін.

Задача формалізується як напівмарковський процес рішень (SMDP): рішення
приймаються лише в моменти подій, час між рішеннями змінний.

Одна спільна Q-мережа для всіх вузлів (parameter sharing), рішення
децентралізовані (кожен вузол — у свій момент), навчання централізоване
(спільний буфер досвіду). Клас обладнання вузла входить у стан.

## 2. Модель надійності та деградації v0.3

### 2.1. Віртуальний вік
- `v_i` — віртуальний вік вузла i (с напрацювання). Зростає лише у стані
  WORKING (як нинішній `time_work`).
- Модель Kijima типу II: після втручання `v ← q · v`, де
  - `q_pm ∈ [0, 1]` — після ТО (0 = «як новий», 1 = без ефекту);
  - `q_cm ∈ [0, 1]` — після ремонту.
- Для контрольної перевірки (Фаза 1, перевірка c) — `q_pm = q_cm = 0`: тоді
  задача для одного вузла зводиться до класичної заміни за віком, для якої
  оптимум розраховується аналітично.

### 2.2. Відмови: розподіл Вейбулла за віртуальним віком
- Інтенсивність відмов: `h(v) = (β/η) · (v/η)^(β−1)`.
- Після кожного втручання залишковий ресурс семплюється умовно на досягнутий
  вік: `t_f = η · [ (v/η)^β − ln U ]^(1/β) − v`, `U ~ Uniform(0,1)`.
- Ймовірність відмови протягом наступної операції тривалістю `d`:
  `p_f(v, d) = 1 − exp( −[ ((v+d)/η)^β − (v/η)^β ] )`.
- Відмова мід-флайт → REPAIR, перервана операція списується в брак
  (наявний механізм D15/D18, без змін).
- β = 1 → експоненційний розподіл (поведінка, еквівалентна моделі Статті 1).

### 2.3. Деградація якості
- Ймовірність браку виробу: `p_def(v) = p0 + (p_max − p0) · (1 − exp(−v/τ_q))`.
- Бракований виріб не потрапляє на склад; його BOM-слід списується в
  `defects` (D15/D18) → квота автоматично розширюється на компенсацію.
- ❓ Для Type0 (філамент, партія 1000 од.) — брак усієї партії чи частки?

### 2.4. Деградація швидкості
- Темп виконання операції: `progress += Δt / s(v)`, де
  `s(v) = 1 + κ · min(v/η, v_cap)` — множник тривалості (≥ 1).

### 2.5. Тривалості втручань
- `d_pm` — тривалість ТО, `d_cm` — тривалість ремонту, за класом обладнання.
  Ключове безрозмірне відношення — `d_pm / d_cm`.
- ❓ Константи (як зараз: 1200 / 10000 с) чи логнормальні з CV?

### 2.6. Випадковість (Р6, пропонується)
Окремий `numpy.random.Generator` на кожну пару (вузол, процес ∈ {відмова,
брак, тривалість}), породжений з master seed через `SeedSequence.spawn`.
Різні політики на одному seed отримують ті самі випадкові «долі» → парні
порівняння.

## 3. Моменти рішень і дії

### 3.1. Моменти рішень (decision epochs)
- **E1** — вузол у IDLE, правило D17 уже обрало наступну операцію, але запит
  на ресурси ще не подано. Тривалість наступної операції `d_next` відома.
- **E2** — вузол щойно перейшов у WAITING_FOR_RESOURCE і ресурси не видано
  в той самий такт.
- **E3** — вузол усе ще чекає ресурс; повторне рішення кожні `Δ_w` с
  (❓ Δ_w = 3600 с?).

### 3.2. Дії
| a | Назва | Ефект |
|---|---|---|
| 0 | CONTINUE | E1: подати запит і працювати; E2/E3: чекати далі |
| 1 | PM | Перейти в MAINTENANCE на `d_pm`; у E2/E3 — спершу відкликати запит з `ResourceManager.requests`, операцію → IDLE |

- Маскування: PM заборонено, якщо `v < v_min` (вузол щойно після ТО) — щоб
  уникнути циклу «ТО → IDLE → ТО».
- Агент **не** обирає тип операції, не змінює тривалостей і пріоритетів черги,
  не «омолоджує» вузол без ціни.

## 4. Стан (вектор спостереження для рішення вузла i)

Усі ознаки детерміновані: обчислюються зі стану симуляції та відомих
параметрів розподілів (без випадкових семплів).

**Локальні ознаки вузла:**
1. клас обладнання (one-hot, K класів);
2. `v_i / η_i` — нормований віртуальний вік;
3. `p_f(v_i, d_next)` — ймовірність відмови під час наступної операції;
4. `p_def(v_i)` — поточна ймовірність браку;
5. `s(v_i)` — поточний множник тривалості;
6. прапорець моменту рішення (E1 / E2 / E3);
7. вже очікуваний час (нормований на `d_next`);
8. покриття входів наступної операції запасом: `min_k(stock_k / need_k)`, обрізане до 1;
9. кількість запитів у черзі на ті самі ресурси попереду;
10. `d_pm / d_next`, `d_cm / d_next`.

**Глобальні ознаки:**
11. частка вузлів у PM/REPAIR (усього і у своєму класі);
12. попит на продукт вузла далі по лінії (функція `_pending_demand` правила D17, нормована);
13. прогрес епізоду: виготовлені придатні дрони / ціль.

Розмірність ≈ K + 13. ❓ Чи додавати історію (останні k рішень) — поки ні.

## 5. Винагорода

### 5.1. Цінність виробу
`V(type)` — втілений час обробки: сума ідеальних тривалостей усіх операцій
BOM-дерева типу (рекурсія `get_bom_footprint`). Безрозмірна після нормування
на `V(Type22)`.

### 5.2. Функція винагороди ❓ (основне відкрите питання)
- **Варіант A — локальна (рекомендовано для старту).** Для переходу вузла i
  від рішення k до рішення k+1:
  `r = Σ V(придатних виробів, виготовлених i) − Σ V(виробів, списаних у брак на i)`
  `− Σ V(спожитого входу, втраченого через відмову мід-флайт на i)`.
  Ціна простою на ТО/ремонт неявна: втрачений час = невироблена цінність.
- **Варіант B — глобальна.** Приріст придатних дронів (і/або втіленої цінності
  всієї лінії) за інтервал. Краще узгоджена з метою, але гірше з розподілом
  заслуг між 26–30 вузлами.

Незалежно від варіанта, **оцінювання — лише на лінійних метриках §7**.

### 5.3. Дисконтування SMDP
`γ(Δt) = exp(−ρ · Δt)`; `ρ` задається через період напіврозпаду (❓ ~1 доба
модельного часу?).

## 6. Епізоди, seed-и, рандомізація

- Кожен епізод — нова лінія (скидання стану). Кінець — `N_target = 10`
  придатних дронів (як у Статті 1) або `T_max` (❓ 5·10⁶ с).
- Seed-и середовища: навчальні `0…9999`, тестові `100000+` — не перетинаються.
- Seed-и агента: ≥ 3 (ініціалізація мережі, ε-жадібність, семплювання буфера).
- Рандомізація параметрів: на кожен навчальний епізод параметри класів
  семплюються з діапазонів таблиці класів; тестові набори — окремі, відкладені.
- `n_filament_suppliers = 5` (❓ як у повній сітці Статті 1).

## 7. Бейслайни і метрики

### 7.1. Бейслайни
| Код | Політика | Параметр налаштування |
|---|---|---|
| B0 | Без ТО (лише ремонт після відмови) | — |
| B1 | Періодичне ТО за напрацюванням (T_pm) | T_pm на клас |
| B2 | ТО за порогом ризику: `p_f(v, d_next) > θ` | θ на клас |
| B3 | Опортуністичне: ТО, якщо вузол чекає ресурс і `v/η > x`; інакше B2 | x, θ на клас |
| B4 | Випадкова з тією самою частотою ТО, що в DQN | — |
| B5 | Поточна логіка симулятора (природний `maintenance_interval`) | — |

Параметри B1–B3 налаштовуються перебором на навчальних seed, найкращі
оцінюються на тестових. Бюджет налаштування документується.

### 7.2. Метрики
**Основна:** makespan для 10 придатних дронів (еквівалентно пропускна
здатність TH = 10 / makespan).

**OEE вузла i** (визначення фіксуємо явно, бо ТО в класичному OEE за Nakajima
часто виключають як плановий простій):
- `A_i = t_run / (t_run + t_pm + t_cm)` — **ТО рахується як втрата доступності**,
  простій через відсутність ресурсу (зовнішній) не рахується;
- `P_i = Σ ідеальних тривалостей виконаних операцій / t_run`;
- `Q_i = придатні / усі завершені`;
- `OEE_i = A_i · P_i · Q_i`; агреговано по лінії — зважено на `t_run`.

**Надійність:** `MTBF_i = t_run_i / n_fail_i`; по лінії — `Σ t_run / Σ n_fail`;
кількість відмов, кількість ТО, частка ТО, проведених під час очікування ресурсу,
рівень браку.

### 7.3. Статистика
Завдяки CRN (Р6) — парні тести: Wilcoxon signed-rank, поправка Холма на
множинні порівняння, bootstrap-довірчі інтервали, розміри ефектів.
